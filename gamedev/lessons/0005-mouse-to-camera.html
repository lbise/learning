① Worked example: how a mouse movement becomes a camera turn

The embedded picture

relative is “the mouse position relative to the previous position”, in pixels.

You already know two ways hardware reports input:

  • A button on a GPIO pin: you poll its level whenever you like. That's Input.is_action_pressed("jump"): keys have a state you can query at any time.
  • A rotary encoder: it fires interrupts carrying tick counts since the last report. There's no absolute position to read, so you accumulate the deltas yourself. Mouse movement works this way. Godot hands you an event with relative (pixels moved since the last event), and you add it to an angle you keep.

The angle you keep is pivot.rotation.y. It's the accumulator.

The path an event takes

The docs: “For gameplay input, Node._unhandled_input() is generally a better fit, because it allows the GUI to intercept the events.” So a click on a menu button won't also swing your camera.

mouse moves
   │  OS → Godot wraps it in an InputEventMouseMotion object
   ▼
_input()            on any node that defines it
   ▼
GUI controls        buttons and menus may consume it
   ▼
_unhandled_input(event)   ← your Player.gd receives it here
   │  you check its type, read event.relative, update the rig
   ▼
pivot.rotation.y / arm.rotation.x change → the camera moves next frame

Godot calls _unhandled_input for every kind of event: key presses, mouse clicks, the wheel, mouse motion. Your job in that function is to sort by type, like a switch on the message ID of a tagged union.

The code, line by line

func _unhandled_input(event: InputEvent) -> void:
	if event is InputEventMouseMotion \
			and Input.mouse_mode == Input.MOUSE_MODE_CAPTURED:
		pivot.rotation.y -= event.relative.x * mouse_sensitivity
		arm.rotation.x -= event.relative.y * mouse_sensitivity
		arm.rotation.x = clampf(arm.rotation.x,
				deg_to_rad(-70.0), deg_to_rad(20.0))
	elif event.is_action_pressed("ui_cancel"):
		Input.mouse_mode = Input.MOUSE_MODE_VISIBLE
	elif event is InputEventMouseButton and event.pressed:
		Input.mouse_mode = Input.MOUSE_MODE_CAPTURED
LineWhat it does and why
event: InputEventThe base type. The actual object is one of its subclasses (mouse motion, mouse button, key, …).
event is InputEventMouseMotionThe type check (“is this message a motion report?”). Inside this branch, Godot lets you use event.relative.
… and mouse_mode == CAPTUREDOnly steer the camera while the mouse is locked, so moving the cursor to another window after Esc doesn't spin the view.
pivot.rotation.y -= relative.x * sensAccumulate horizontal movement into yaw on the pivot. Units: pixels × (rad/pixel) = rad. 100 px × 0.003 = 0.3 rad ≈ 17°. The minus sign: in Godot a positive Y rotation turns left (counter-clockwise from above), and moving the mouse right should turn right.
arm.rotation.x -= relative.y * sensVertical movement goes to pitch on the other node, the arm. One axis per node.
clampf(…, -70°, 20°)Limit the accumulator so the camera can't flip over the top or dive under the floor. Same idea as saturating an integrator.
ui_cancel → VISIBLEEsc is a built-in action. Releasing the mouse is how players get out of the game window.
InputEventMouseButton and pressedAny click recaptures the mouse. pressed filters out the release half of the click.

pivot and arm come from @onready var pivot: Node3D = $CameraPivot, the same node-path lookup as $HUD/ScoreLabel in Lesson 3.

Check your understanding: predict, then try it

1. You delete the minus sign: pivot.rotation.y += …. What does the player experience?

Show answerInverted horizontal look: moving the mouse right turns the view left. Many games offer exactly this as an “invert X” option. It's one sign.

2. You accidentally write pivot.rotation.x instead of .y on the first line. What happens?

Show answerMoving the mouse sideways now tilts the camera up and down around the pivot, unclamped, so it can flip right over. The pitch from the arm adds on top. This is why one axis per node keeps things understandable.

3. A colleague moves the mouse code into _physics_process using Input.is_action_pressed. Why can't that work?

Show answerMouse motion isn't an action with a held state. It's a stream of delta reports, like encoder ticks. You have to receive the events.

② Completion: mouse-wheel zoom

The wheel arrives as an InputEventMouseButton, the same type as a click. Its button_index tells you which “button” it was. You'll compare it to the constants MOUSE_BUTTON_WHEEL_UP and MOUSE_BUTTON_WHEEL_DOWN. Zoom means changing arm.spring_length (metres).

Replace the last elif branch of your _unhandled_input with this skeleton, add the three @exports at the top, and fill in the four TODOs:

@export var zoom_step := 0.5   # metres per wheel notch
@export var min_zoom := 2.0
@export var max_zoom := 10.0

# … inside _unhandled_input, replacing the old MouseButton branch:
	elif event is InputEventMouseButton and event.pressed:
		if event.button_index == MOUSE_BUTTON_WHEEL_UP:
			pass  # TODO 1: zoom in, so the arm gets shorter
		elif TODO 2: the other wheel direction:
			pass  # TODO 3: zoom out
		else:
			Input.mouse_mode = Input.MOUSE_MODE_CAPTURED   # real clicks still recapture
		# TODO 4: keep arm.spring_length between min_zoom and max_zoom

Done when: scrolling up moves the camera closer, scrolling down moves it away, and it stops at 2 m and at 10 m.

Hint (only if stuck)

Show hintTODO 4 is the same pattern as the pitch clamp a few lines above, just with spring_length and your two exports. TODOs 1 and 3 are -= and += with zoom_step.

Solution

Show solution 
	elif event is InputEventMouseButton and event.pressed:
		if event.button_index == MOUSE_BUTTON_WHEEL_UP:
			arm.spring_length -= zoom_step
		elif event.button_index == MOUSE_BUTTON_WHEEL_DOWN:
			arm.spring_length += zoom_step
		else:
			Input.mouse_mode = Input.MOUSE_MODE_CAPTURED
		arm.spring_length = clampf(arm.spring_length, min_zoom, max_zoom)
I ran this in Godot 4.7.2 without a window: 30 wheel-up events from 5 m stopped at exactly 2.0 m.

A note on reading the docs

From the docs' own guide to learning new features.

You said looking things up in the docs felt like it defeated the purpose. Half of that is right: a lesson shouldn't make you discover the core idea, and Lesson 4 did. But looking up details is a core skill, not cheating. Every Godot developer does it constantly. Two shortcuts make it fast:

  • In the script editor, hold Ctrl and click a class, method or property name to jump to its documentation.
  • F1 (Help → Search Help) searches the built-in class reference offline.

Practise on purpose: Ctrl+click InputEventMouseButton in your script and find the property that holds the wheel's precise scroll amount on trackpads. (It's factor, but find it yourself.) That's the kind of lookup you'll do while building games.

③ On your own: sprint

Everything you need, you've already used in Lessons 1–2. No new concepts.

  1. Holding Shift makes the player move twice as fast. Releasing it returns to normal speed.
  2. The multiplier can be tuned in the Inspector.
  3. Sprinting doesn't change jump height.
  4. Your code checks an input action named by intent, never a raw key.

Solution: open only after your own attempt works or you've tried for 15 minutes

Show solution Add a sprint action bound to Shift in the Input Map, then: 
@export var sprint_multiplier := 2.0

# in _physics_process, before setting velocity.x / .z:
	var current_speed := speed
	if Input.is_action_pressed("sprint"):   # held → pressed, not just_pressed
		current_speed *= sprint_multiplier
	velocity.x = direction.x * current_speed
	velocity.z = direction.z * current_speed
Tested: 1 s of walking covered 5 m, and 1 s of sprinting covered 10 m. Jump height is untouched because only the horizontal components use current_speed.
