One state at a time

Replace flags and if-ladders with a finite state machine, then add landing and a dodge roll without the code turning to spaghetti.

Warm-up: from memory

Who should connect the all_coins_collected signal to Player.celebrate, and why not the player itself?

Show answerThe world, or an editor connection saved in world.tscn: the node that knows both sides. If the player connected itself, it would have to find its level, and the reusable scene would then depend on that level.

From Lesson 6: play("Walk") every tick while Walk is already playing. Does it restart?

Show answerNo, it continues. Only a finished non-looping clip restarts.

Show answerChildren first, then the parent.

① Worked example: from flags to states

The smell

Your Lesson 6 player has celebrating (a flag), an early return, and an if-ladder in update_animation. Now imagine adding landing, rolling, attacking and swimming. Can you roll while celebrating? Jump mid-roll? Every new flag multiplies the combinations you have to think about. Robert Nystrom describes exactly this in Game Programming Patterns: “When you have a handful of flags where only one is true at a time, that's a hint that what you really want is an enum.”

You've probably written this in C: switch (state) inside the superloop. GDScript's version is an enum plus match.

A finite state machine says that the character is in exactly one state at a time. Each state decides what happens each tick and when to leave, and entering a state runs its one-time setup, such as starting an animation.

            jump / walked off edge
   IDLE ⇄ MOVE ───────────────────▶ AIR
     ▲                                 │ touches floor
     │ anim finished / input           ▼
     └──────────────────────────── LAND      (② you add this)

   IDLE/MOVE ── roll pressed ──▶ ROLL ── anim finished ──▶ IDLE   (③ on your own)
   any ── all coins collected ──▶ CELEBRATE

The pattern: three pieces

PieceJob
enum State + var stateThe single source of truth: “what am I doing right now?”
match state: in _physics_processPer-tick behaviour and exit conditions for the current state
change_state(new)The only place state is assigned. It runs enter actions (start an animation, store a direction) exactly once

The refactored player.gd

This replaces the movement part of your script and keeps _ready's mouse capture and _unhandled_input as they are. It's long, but there's almost nothing new in it: the same pieces you wrote, rearranged.

extends CharacterBody3D

enum State { IDLE, MOVE, AIR, CELEBRATE }

# … your @export vars and @onready vars from before (speed, anim, pivot, model …)

var state := State.IDLE

func _physics_process(delta: float) -> void:
	if not is_on_floor():
		velocity += get_gravity() * delta        # gravity applies in every state

	var input := Input.get_vector("move_left", "move_right",
			"move_forward", "move_back")
	var direction := Vector3(input.x, 0, input.y).rotated(Vector3.UP, pivot.rotation.y)
	var sprinting := Input.is_action_pressed("sprint")

	match state:
		State.IDLE, State.MOVE:
			walk(direction, sprinting, delta)
			if Input.is_action_just_pressed("jump") and is_on_floor():
				velocity.y = jump_velocity
				change_state(State.AIR)
			elif not is_on_floor():
				change_state(State.AIR)              # walked off an edge
			elif direction.length() > 0.01:
				change_state(State.MOVE)
				anim.play("Sprint" if sprinting else "Walk", anim_blend)
			else:
				change_state(State.IDLE)
		State.AIR:
			walk(direction, sprinting, delta)        # air control
			if is_on_floor():
				change_state(State.IDLE)             # ② will route this via LAND
		State.CELEBRATE:
			velocity.x = 0
			velocity.z = 0

	move_and_slide()

func change_state(new_state: State) -> void:
	if new_state == state:
		return                                   # enter actions run once, not every tick
	state = new_state
	match state:
		State.IDLE:
			anim.play("Idle", anim_blend)
		State.AIR:
			anim.play("Jump", anim_blend)
		State.CELEBRATE:
			anim.play("Dance", anim_blend)

func walk(direction: Vector3, sprinting: bool, delta: float) -> void:
	var current_speed := speed * (sprint_multiplier if sprinting else 1.0)
	velocity.x = direction.x * current_speed
	velocity.z = direction.z * current_speed
	if direction.length() > 0.01:
		var target_yaw := atan2(-direction.x, -direction.z)
		model.rotation.y = lerp_angle(model.rotation.y, target_yaw, turn_speed * delta)

func celebrate() -> void:
	change_state(State.CELEBRATE)

Things to notice:

  • celebrating, the early return and update_animation are gone. CELEBRATE simply has no transitions out, so it's a terminal state.
  • State.IDLE, State.MOVE: shares one branch between two states. They differ only in their animation.
  • MOVE still calls anim.play every tick, so switching between walk and sprint works mid-move. That's safe because play on the current clip continues it.
  • walk() was pulled out because two states use it. Nothing in it is new.

Predict, then try

1. Delete the if new_state == state: return guard. What changes on screen?

Show answerVery little for Idle, because play on the current clip continues. But every enter action now runs every tick. Once you add a one-shot like LAND or ROLL in ② and ③, it would restart every frame and never finish. The guard is what makes “enter” mean enter.

2. Can the character jump while celebrating? Point to the line that decides it.

Show answerNo. The jump check exists only in the IDLE, MOVE branch. In a state machine, “can I do X in state Y?” is answered by looking at a single branch, not by working through every combination of flags.

② Completion: landing

The clip "Jump_Land" is a one-shot (no loop token, so it plays once). At normal speed it lasts 1.27 s, which is far too long to lock the player, so play it faster and let movement cancel it. You'll need one new tool: AnimationPlayer's animation_finished(anim_name) signal, which “notifies when an animation finished playing”. The docs add: “This signal is not emitted if an animation is looping.”

enum State { IDLE, MOVE, AIR, LAND, CELEBRATE }      # + LAND
@export var land_anim_speed := 2.0

func _ready() -> void:
	# … existing lines …
	# TODO 1: connect anim.animation_finished to _on_animation_finished

# in _physics_process:
		State.AIR:
			walk(direction, sprinting, delta)
			if is_on_floor():
				# TODO 2: go to LAND instead of IDLE
		State.LAND:
			# TODO 3: if there's movement input, cancel into MOVE.
			#         Otherwise stand still (zero horizontal velocity).

# in change_state's match:
		State.LAND:
			anim.play("Jump_Land", 0.1, land_anim_speed)   # args: name, blend, speed

func _on_animation_finished(anim_name: StringName) -> void:
	# TODO 4: if we're still landing, go back to IDLE
	pass

Done when: a jump ends with a short landing animation, standing still afterwards returns to idle, and pressing a direction during the landing walks away immediately.

Hint

Show hintTODO 1 is the same pattern as body_entered.connect(...) in your coin. TODO 4 must check the state, because the signal fires for any finished one-shot. If movement already cancelled the landing, you're in MOVE and should stay there.

Solution

Show solution 
	anim.animation_finished.connect(_on_animation_finished)   # TODO 1

				change_state(State.LAND)                       # TODO 2

		State.LAND:                                        # TODO 3
			if direction.length() > 0.01:
				change_state(State.MOVE)
			else:
				velocity.x = 0
				velocity.z = 0

func _on_animation_finished(anim_name: StringName) -> void:   # TODO 4
	if state == State.LAND:
		change_state(State.IDLE)
Tested in Godot 4.7.2 without a window: walk, jump, AIR (Jump), touch down, LAND (Jump_Land at 2×), animation finished, IDLE.

Debugging puzzle: when the game starts, the character plays the landing animation once, without ever jumping. Why?

Show answeris_on_floor() reports the result of the last move_and_slide(). On the very first tick there hasn't been one yet, so it's false. IDLE goes to AIR, and the next tick goes from AIR to LAND. It's harmless here, but it's a classic first-frame bug. (Lesson 2 quoted that same last call wording.)

③ On your own: dodge roll

The clip is "Roll" (a one-shot, 1.47 s). Everything you need is now in your script.

  1. A new roll input action (pick a key, e.g. C or Alt) starts a roll from IDLE or MOVE, on the floor only.
  2. The roll goes in the direction the character faces when it starts, at a tunable roll_speed. Steering input during the roll is ignored.
  3. The roll animation plays at a tunable speed (try 1.5×). When it finishes, the character returns to IDLE.
  4. You can't jump or start another roll mid-roll. Gravity still applies.

Hint: which way is “facing”?

Show hintYour facing code points the Model's −Z axis at the movement direction, so the facing direction is -model.global_basis.z. global_basis is the node's rotation in world space. Store it once, in the enter action, flattened (y = 0) and normalized.

Solution

Show solution 
enum State { IDLE, MOVE, AIR, LAND, ROLL, CELEBRATE }
@export var roll_speed := 7.0
@export var roll_anim_speed := 1.5
var roll_direction := Vector3.ZERO

# IDLE/MOVE branch, after the jump check:
			elif Input.is_action_just_pressed("roll") and is_on_floor():
				change_state(State.ROLL)

		State.ROLL:
			velocity.x = roll_direction.x * roll_speed
			velocity.z = roll_direction.z * roll_speed

# change_state:
		State.ROLL:
			roll_direction = -model.global_basis.z
			roll_direction.y = 0
			roll_direction = roll_direction.normalized()
			anim.play("Roll", 0.1, roll_anim_speed)

# _on_animation_finished:
	if state == State.LAND or state == State.ROLL:
		change_state(State.IDLE)
Tested: the roll held its starting direction while D was pressed, lasted about 1 s at 1.5×, then went back to IDLE and on to MOVE.

Godot also has a visual state machine for animations, AnimationTree's StateMachine, which handles blending as well. You'll understand it far faster now that you've built the logic by hand.
