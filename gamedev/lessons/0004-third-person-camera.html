Show answerA node does something and lives in the scene tree (Camera3D, CollisionShape3D). A resource is a data container that nodes use (BoxMesh, StandardMaterial3D).

The concepts you need

1. One axis per node

A third-person camera turns left and right (yaw, around Y) and tilts up and down (pitch, around X). The standard trick is to give each axis its own node: a parent that only yaws and a child that only pitches. Nesting them combines the rotations in the right order for free, the same way the orbiting cube rode along on its parent in Lesson 1.

Second rule: don't rotate the CharacterBody3D to face movement. Anything parented to it, including the camera rig, would spin along with it. Rotate a child Model node that holds only the visuals.

2. SpringArm3D: a camera boom that won't clip

The 3D docs explain why you need one: with a plain child camera, “the camera clips through geometry and hides the scene.”

SpringArm3D “casts a ray or a shape along its Z axis and moves all its direct children to the collision point”. Put the camera at the end of it and the camera slides closer to the player when a wall gets in the way. Its length is the spring_length property (default 1 m, which is far too short).

3. The mouse is an event, not a state

Keys can be polled (“is W held?”), but mouse movement arrives as events. Override _unhandled_input(event), which is called for input the UI didn't consume, and read InputEventMouseMotion.relative, the movement since the last event in pixels. To hide and lock the cursor, set Input.mouse_mode = Input.MOUSE_MODE_CAPTURED. The docs say you then need relative to read motion.

4. Camera-relative movement

Right now, W always moves toward −Z in the world. In a third-person game, W means “away from the camera”. So build the input vector as before, then rotate it around Vector3.UP by the camera's yaw, using Vector3.rotated(axis, angle). You know this as a 2D rotation matrix in disguise.

5. Facing a direction, and the angle wrap trap

Remember this for later: Godot's “forward” is −Z, but imported 3D assets face +Z (Vector3.MODEL_FRONT). When you swap the capsule for a real character, it may walk backwards, and now you'll know why.

Turning a direction vector into a yaw angle is atan2. Smoothing the turn needs care: going from 170° to −170° is a 20° turn, but a plain lerp would sweep 340° the long way. lerp_angle(from, to, weight) “interpolates correctly when the angles wrap around”.

Add a small box “nose” to the model so you can see which way it faces. Put it on the model's −Z side.

The spec

Modify your player.tscn and player.gd from Lessons 2–3. Tick each criterion off when you've tested it in game:

  1. The mouse is captured when the game starts. Moving it left and right orbits the camera around the player.
  2. Moving the mouse up and down tilts the camera, clamped so it can't flip over the top or go under the floor.
  3. Esc releases the mouse. Clicking in the window captures it again.
  4. W moves away from the camera whichever way the camera faces. A, S and D behave the same way relative to the camera.
  5. The model turns smoothly to face its movement direction. The camera does not turn with it.
  6. Back the player against a crate stack: the camera pulls in instead of disappearing inside it.
  7. Coins, jumping and the score still work.

Hint 4: the facing angle

Show hint A model whose front is −Z, yawed by θ, faces (−sin θ, 0, −cos θ). Setting that equal to direction gives θ = atan2(-direction.x, -direction.z). Only update it while actually moving (direction.length() > 0.01), or the model snaps back to 0 when you let go.

Full solution: player.gd (tested in Godot 4.7.2)

Show solution 
extends CharacterBody3D

@export var speed := 5.0
@export var jump_velocity := 4.5
@export var mouse_sensitivity := 0.003   # radians per pixel
@export var turn_speed := 10.0           # higher = snappier turning

@onready var pivot: Node3D = $CameraPivot
@onready var arm: SpringArm3D = $CameraPivot/SpringArm3D
@onready var model: Node3D = $Model

func _ready() -> void:
	add_to_group("player")
	Input.mouse_mode = Input.MOUSE_MODE_CAPTURED

func _unhandled_input(event: InputEvent) -> void:
	if event is InputEventMouseMotion and Input.mouse_mode == Input.MOUSE_MODE_CAPTURED:
		pivot.rotation.y -= event.relative.x * mouse_sensitivity
		arm.rotation.x -= event.relative.y * mouse_sensitivity
		arm.rotation.x = clampf(arm.rotation.x, deg_to_rad(-70.0), deg_to_rad(20.0))
	elif event.is_action_pressed("ui_cancel"):
		Input.mouse_mode = Input.MOUSE_MODE_VISIBLE
	elif event is InputEventMouseButton and event.pressed:
		Input.mouse_mode = Input.MOUSE_MODE_CAPTURED

func _physics_process(delta: float) -> void:
	if not is_on_floor():
		velocity += get_gravity() * delta
	if Input.is_action_just_pressed("jump") and is_on_floor():
		velocity.y = jump_velocity

	var input := Input.get_vector("move_left", "move_right",
			"move_forward", "move_back")
	var direction := Vector3(input.x, 0, input.y).rotated(Vector3.UP, pivot.rotation.y)
	velocity.x = direction.x * speed
	velocity.z = direction.z * speed

	if direction.length() > 0.01:
		var target_yaw := atan2(-direction.x, -direction.z)
		model.rotation.y = lerp_angle(model.rotation.y, target_yaw, turn_speed * delta)

	move_and_slide()
I checked it in Godot 4.7.2 without a window: with the camera yawed 90°, holding W moved the player 5 m along −X in one second, and the model turned to 90°. A wall behind the player shortened the arm from 5 m to about 2.7 m.

Stretch goals (pick any)

  • Zoom: the mouse wheel changes arm.spring_length, clamped to 2–10 m. Wheel events are InputEventMouseButton with MOUSE_BUTTON_WHEEL_UP or MOUSE_BUTTON_WHEEL_DOWN.
  • Sprint: a new sprint input action (Shift) that multiplies speed while held. Which of is_action_pressed or is_action_just_pressed do you need?
  • For the control engineer: lerp(x, target, k * delta) is a first-order low-pass filter, but it's only approximately frame-rate independent, and it overshoots once k * delta > 1. Replace the weight with 1.0 - exp(-turn_speed * delta) and explain why that's exact.
